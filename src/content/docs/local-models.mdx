<DocSection title="What This Is">

A model here is a directory on your disk. You point at it, and it runs
on your machine against the font you have open. Nothing is downloaded,
no account is needed, and your drawings are not sent anywhere.

<Callout>
  This is experimental in a way the rest of the editor is not. The
  mechanism is sound and the guardrails are real, but the models are
  small and early, and what they propose is often wrong. Treat every
  result as a suggestion to judge, never as an answer.
</Callout>

</DocSection>

<DocSection title="Getting a Model">

You train one, or you are given a directory by someone who did. The
editor downloads nothing.

The quickest way to have one is the
[local AI demo repo](https://github.com/eliheuer/runebender-local-ai-demo):
it holds a small font family made for training, a script that trains a
model on it in about a minute, and a checked-in copy of that model.
[Set up local AI](/docs/local-ai-setup.html) walks through it.

Put a model in `~/Runebender/models` and the editor lists it at
startup. Drawing models sit there by kind, `shapes/` and `bolden/`;
each chat model is its own folder directly under the root, named as you
want it listed. Installing a model is dropping the folder there. Set
`RUNEBENDER_MODELS` to read them from somewhere else, or list more
directories, one per line, in `~/.runebender/model_paths` or
`RUNEBENDER_MODEL_PATHS`. The old `~/.runebender/models` folder is
still read, but nothing is written there.

Open-weight language models for the Chat panel are a directory holding
one `.gguf` file, `model.gguf` by convention, under the same roots. An
optional `model.json` beside it sets that model's server defaults; its
keys are `context`, `thinking`, `temperature`, `top_p`, `top_k`,
`min_p`, `presence_penalty` and `template_kwargs`. An optional
`mmproj*.gguf` from the same model repository is the vision projector,
which lets the model look at proof pictures. These models are 3 to 22
gigabytes; you download them yourself from Hugging Face, and
[Set up local AI](/docs/local-ai-setup.html) names the ones in use.

A shape or bolden model is three files:

<table>
  <caption>What a model directory holds</caption>
  <tbody>
    <tr><th><code>config.json</code></th><td>Shape of the network, and which kind of model it is.</td></tr>
    <tr><th><code>weights.safetensors</code></th><td>The trained weights.</td></tr>
    <tr><th><code>vocab.txt</code></th><td>The glyph names it was trained on.</td></tr>
  </tbody>
</table>

Nothing else is read, and the directory is inspectable: `cat` the
config to see what you have.

</DocSection>

<DocSection title="Boldening">

Open the Local AI section of the left panel and choose a model under
Model. The editor remembers it for the session.

Open a glyph in the lighter master and click Bolden This Glyph under
Tasks, or Bolden Every Glyph for the whole master. The editor predicts
a heavier version.

The result waits under Proposals. Compare shows it against the
current drawing, Install writes it as an ordinary edit, and Discard
drops it. After an install, Undo Install takes it back.

Glyph → Bolden With Model… does the same thing from the menu.

<table>
  <caption>What you get</caption>
  <tbody>
    <tr><th>Status line</th><td>How many points moved, of how many, and the change in advance width.</td></tr>
    <tr><th>Proposals</th><td>The prediction, ready to compare, install, or discard.</td></tr>
  </tbody>
</table>

</DocSection>

<DocSection title="Why It Cannot Break Compatibility">

A Bold master has to stay point-compatible with its Regular: the same
contours, the same points, in the same order. Break that and the
family stops interpolating.

The prediction cannot break it. Every drawing command and every source coordinate is fixed from the
glyph you already have. The model fills in only the offsets between
them, chosen from a range of distances. There is no point in the process at which it could
add, remove, or reorder a point. It moves points, and that is all it
can do.

The editor checks the result anyway before writing, and refuses if the
number of offsets does not match the number of points.

<Callout>
  The risk is not a broken font. It is a bad drawing, which you can see
  and undo.
</Callout>

</DocSection>

<DocSection title="Strength">

The slider under the model row scales how far the predicted points
move. 1.00x applies the prediction as it came.

Leave it at 1.00x unless you have a reason. Measured over 71 held-out
glyphs, raising the strength made the result worse at every step. The
model does not under-move uniformly. Scaling amplifies its mistakes
along with its good guesses.

The slider is for a model that is right about direction and short on
distance. That is a property of one model, not a general fix.

</DocSection>

<DocSection title="Scoring a Prediction">

The Score node in [Graph](/docs/workflows.html) does this when both
masters have the glyph drawn. It compares the prediction to the drawing you already
made. It reports two numbers: the model's average error per point, and
the error from shifting every point by the average amount.

Lower is better, and the second number is the one to beat. A model
that cannot beat a uniform shift is not telling you anything a
constant could not.

This works only on glyphs you have already drawn in both masters. It
measures a model on known work before you trust it on unknown work.

</DocSection>

<DocSection title="What to Expect">

Quality varies by glyph, and not evenly. Running the Virtua-12M model
on Virtua Grotesk, `H` moves all 25 of its points and thickens
sensibly; `eight` moves only 15 of its 53, and the result needs work.
Straight stems are easier to be right about than curves.

Read the moved-point count in the status line as a rough confidence
signal. A glyph where most points stayed put is one the model had
little to say about.

A good average score does not mean a usable drawing. Average point
error says nothing about whether stems landed on the weights the
family uses, which is what decides if a glyph reads correctly. Judge
the drawing with your eyes and use the score to compare models.

</DocSection>

<DocSection title="From the Command Line">

The same models run outside the editor through
[font-ml](https://github.com/eliheuer/font-ml), which is where the
inference lives. Useful for trying a model over many glyphs before
bringing it into a drawing session.

<CommandList commands={[
  "font-ml describe <model>",
  "font-ml run bolden --model <model> --source Font.ufo --glyph eight",
]} />

`describe` reports what a model is and which jobs it can do, and every
command takes `--json`.

</DocSection>

<DocSection title="Chat">

The Chat panel in the left rail talks to a local language model about
the open font. Pick a model from the list of rows. The editor serves
it through a supervised `llama-server`: the copy bundled in the app,
then `RUNEBENDER_LLAMA_SERVER`, then PATH and Homebrew
(`brew install llama.cpp`). The server stops when the model changes,
the panel closes, or the editor quits.

When a `llama-server` in router mode is already running on
`127.0.0.1:8080` and lists the chosen model, Chat uses it instead of
starting its own, so one copy of the model serves the editor and any
coding agent on the machine. Start one with
`llama-server --models-dir ~/Runebender/models --port 8080`; a
`presets.ini` in the models folder gives each model its settings, one
`[folder-name]` section per model with `llama-server` arguments as keys.

The model reads and measures glyphs through the same tools as
[MCP](/docs/mcp.html). Edits come back as proposals for you to judge.

Talk records a spoken request and puts the words in the text field
for you to check before sending. It needs whisper.cpp's
`whisper-server` (`brew install whisper.cpp`, or set
`RUNEBENDER_WHISPER_SERVER`) and a speech model saved as `model.bin`
in a model folder whose name starts with `whisper`. The button is
hidden until both are found.

Chat needs the desktop application on macOS or Linux.

</DocSection>

<DocSection title="What Is Not Here">

For an external conversation connected to the live editor, start with
[MCP](/docs/mcp.html). Neither Chat nor MCP currently provides
complete glyph generation from a description. Kerning and spacing models
are named in font-ml and not built.

</DocSection>
