<DocSection title="Choose an Agent Surface">

For interactive type design, start with [MCP and OMP](/docs/mcp.html).
The agent reads the live document, including unsaved edits, and proposes
changes. You review and install those proposals in the editor, with undo.
OMP is the recommended starting client; other local stdio MCP clients can
use the same tools.

File-based automation remains useful for builds and batch work. It reads
saved sources, and the editor can reload external changes when they do not
conflict with unsaved work. Use the live connection when the agent needs
the drawing currently on your canvas.

Use screen control only to judge visual output or operate a UI-only command.
For geometry, metrics, and text data, the live tools are a more exact contract
than pixels. For a saved build or a repeatable batch change, use the UFO and
designspace files instead of a live session.

</DocSection>

<DocSection title="Model Access and Data">

Your external agent handles its own model login. Runebender does not need
an API key for MCP. When the agent uses a hosted model, prompts and the
font data returned to that model go to its provider.

The native GPUI chat pane can also run a local model through
[font-ml](/docs/local-models.html). That is a separate inference choice
from connecting OMP to the editor.

</DocSection>

<DocSection title="Give an Agent Minimum Context">

An agent works better on a font repository than on a loose UFO. Give
it the same things a new collaborator would need.

1. Put the sources in a repository, so every edit is reviewable and
   revertible.
2. Write down the build and check commands where the agent will read
   them.
3. Say what the font's rules are: the grid, the metrics, the naming.
4. Point it at the smallest relevant Runebender page first; use
   `https://runebender.org/llms-full.txt` only when it needs the whole manual.

<CommandList commands={[
  "runebender-gpui sources/Font.designspace",
  "curl -O https://runebender.org/llms-full.txt",
]} />

Agents read a repository's own instructions file, `AGENTS.md` or
`CLAUDE.md`, before anything else. That file is where the font's
rules belong. A compact `DESIGN.md` should name the approved reference glyphs,
their mark meanings, the target masters, and the acceptance check. Do not make
the agent infer those facts from the whole source tree.

</DocSection>

<DocSection title="Start Every Font with a Small Context Bundle">

Copy the public [design brief template](/design-brief-template.md) to a font
repository as `DESIGN.md`, then fill in only the rules that matter to that
family. It keeps the font's evidence—masters, metrics, references, proof
strings, and acceptance criteria—close to the sources.

The [agent capability map](/agent-capabilities.json) is a compact,
machine-readable routing and safety guide. It identifies the live MCP,
saved-source, local-model, and screen-control surfaces without duplicating
the live API. In a connected MCP session, `tools/list` remains authoritative
for exact tool schemas and current availability.

For a new task, an agent should read its repository instructions, `DESIGN.md`,
the capability map, and one relevant documentation page. It should not load the
full manual or inspect the entire source tree unless the task actually needs it.

</DocSection>

<DocSection title="Preserve Font Invariants">

Type design has constraints that are invisible in a diff and
expensive to undo. State them, because an agent will not infer them.

<table>
  <caption>The rules worth writing down</caption>
  <tbody>
    <tr><th>Point compatibility</th><td>Masters must keep the same contours, the same points, in the same order. Break it and the family stops interpolating.</td></tr>
    <tr><th>Contour direction</th><td>Outer contours run one way and counters the other. A reversed contour fills a hole.</td></tr>
    <tr><th>Start points</th><td>Rotating where a contour starts is invisible in one master and fatal across two.</td></tr>
    <tr><th>The grid</th><td>If the family is drawn on a unit grid, say the number. Off-grid points survive every check and ruin the drawing.</td></tr>
    <tr><th>Components</th><td>Decomposing is easy and rarely reversible. Say when it is allowed.</td></tr>
    <tr><th>Sidebearings</th><td>Preserving an advance width is not the same as preserving spacing.</td></tr>
  </tbody>
</table>

<Callout>
  Ask for a check after every batch, not at the end. A compatibility
  break found after fifty glyphs costs fifty glyphs.
</Callout>

</DocSection>

<DocSection title="Separate Proposals from Accepted Work">

An agent produces more drawings than you can review carefully, so
separate what it made from what you have accepted.

Mark colors do this. The glyph grid shows them, and the mark travels
in the source, so the state survives a restart and a git clone. One
workable protocol: the agent marks everything it touches with one
color, and only you may set the color that means done.

Runebender stores the meaning of a mark, not just its color, so a
theme can draw it differently without changing the font. See
[File format](/docs/format.html).

</DocSection>

<DocSection title="Use the Command Line for Saved Sources">

`runebender-core` runs the editor's own operations without a window. Same
code, no interface.

<CommandList commands={[
  "runebender-core bolden --from Light.ufo --to Bold.ufo",
]} />

Every command takes `--json`. The exit codes are 0 ok, 2 usage, 4
failed, so a script can branch without reading text.

</DocSection>

<DocSection title="Use MCP for the Live Editor">

The [MCP guide](/docs/mcp.html) covers OMP setup, finding the open editor,
choosing a master, and reviewing proposals. Start with a read-only request,
then a small proposed edit and an undo test.

`runebender-core mcp --live` discovers native editor sessions. The separate
`--font` mode works on saved sources and cannot see unsaved changes.

</DocSection>

<DocSection title="Build Purpose-Made Tools on Core">

For a tool rather than a session, `runebender-core` is the editing
model as a Rust library with no interface attached. It carries the
operations the editor itself uses: point edits, components, curve
analysis, measurement, shaping, kerning with group fallback.

An agent writing Rust can build a tool on it that makes exactly the
edit you want, instead of driving a general one. See
[Development](/docs/development.html).

</DocSection>

<DocSection title="Run Local Models Deliberately">

`font-ml` runs machine-learning models over font sources from the
command line. Every command takes `--json`. The exit codes separate a
usage mistake from an unimplemented job from a real failure, so an
agent can tell what went wrong.

<CommandList commands={[
  "font-ml tasks",
  "font-ml describe <model>",
  "font-ml run bolden --model <model> --source Font.ufo --glyph eight",
]} />

Run `font-ml tasks` before trusting a job exists. Most are declared
and not built. See [Local models](/docs/local-models.html).

Models live in `~/.runebender/models`. A model is a folder holding
`config.json`, so installing one is putting it there. The editor lists
what it finds at startup. `RUNEBENDER_MODELS` overrides the location.

For a one-shot assistant-guided installation, see
[Set up local AI](/docs/local-ai-setup.html). It uses the same default root for
chat and outline models, verifies the installed capabilities, and keeps the
first smoke test away from a real font.

</DocSection>

<DocSection title="Use Screen Control Only for Visual Work">

An agent that controls the screen can use Runebender the way a person
does, because it is an ordinary desktop application.

For precise font edits, prefer the live geometry tools and review their
proposals. Screen coordinates are a less precise contract for an outline
than points and measurements in font units.

Reach for screen control only for what has no other path, such as
judging how something looks.

</DocSection>

<DocSection title="Current Boundaries">

No way for the application to call a model service. Runebender has no
account system and stores no keys. The chat pane in the editor runs
an open-weight model on your machine through font-ml, and its tools
are the same proposal-only list an agent gets: it can read the font
and propose, and a person installs.

The current recommended workflow keeps hosted-model conversation in OMP
and font editing in Runebender. Embedded hosted-model chat is not part of
this workflow. See [MCP](/docs/mcp.html) for the current tool limits.

</DocSection>
